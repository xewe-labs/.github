# AGENTS.md — xewe-labs

Rules for coding agents working in any xewe-labs repository. A repository's own `AGENTS.md` or
`CLAUDE.md` describes that repository and wins where the two disagree. Agents are first-class users
of this ecosystem: the commands below are the same ones a human runs.

## The ecosystem

| Repository | What it is | Its agent rules |
|---|---|---|
| `xewe-os` | the firmware template users clone; holds only its own code and `xewe.lock` | [`xewe-os/AGENTS.md`](https://github.com/xewe-labs/xewe-os/blob/main/AGENTS.md) |
| `xewe-os-core` | the `XeWeCore` Arduino library (utils, serial, cli, nvs, `XeWeOs`, `xewe::Module`) | [`xewe-os-core/doc/AGENTS.md`](https://github.com/xewe-labs/xewe-os-core/blob/main/doc/AGENTS.md) |
| `xewe-os-modules` | every module, `modules/<slug>/`, plus `CONTRACT.md` and `tools/validate.py` | [`xewe-os-modules/AGENTS.md`](https://github.com/xewe-labs/xewe-os-modules/blob/main/AGENTS.md) |
| `xewe-os-tools` | `xewe`: setup, build, flash, serial, test, boards, modules, lock, release | [`xewe-os-tools/AGENTS.md`](https://github.com/xewe-labs/xewe-os-tools/blob/main/AGENTS.md) |
| `publish-arduino-library` | checks and releases XeWeCore | its own README |

Why it is shaped this way:
[`xewe-os/ARCHITECTURE.md`](https://github.com/xewe-labs/xewe-os/blob/main/ARCHITECTURE.md).

## Never do these without being asked

* **Git writes.** Agents never run a git command that changes state (commit, tag, push, init,
  history rewrites, branch changes) and never create, rename or archive repositories, pull requests
  or GitHub releases. `xewe release` only *prints* the git/gh commands; leave them for a human.
  Tags and registry entries are public and effectively permanent: a published library version can
  never be reused.
* **Touch `~/.arduino15` or `~/Arduino`,** or run `arduino-cli` directly. The tools use an
  isolated environment under the project's `build/`; reuse an installed core with
  `./setup.sh --arduino-data DIR`.
* **Flash a board or require one.** No `--require-board`, `--erase` or `xewe flash` to a real
  port unless the user asks. Compiling is always fine.
* **Edit `xewe.lock`.** Only `xewe lock update`, `xewe modules select`, `xewe setup --modules` and
  `xewe release` write it, and only when asked.

## Code rules that break silently

* **The one include is `#include <XeWeCore.h>`.** arduino-cli discovers a library only from its
  top-level headers; a sketch or module whose only XeWeCore include is `<XeWeCore/<Part>.h>` does
  not build. Sub-headers may follow the umbrella.
* **Module constructors name the Os parameter `host`.** The member is `os`; a parameter named `os`
  hides it. Use `os.serial`, `os.nvs`, `os.cli` in bodies, never `this->os`.
* **Handlers capture `[this]` only.** `[&]` silently binds a shadowing parameter.
* **Never write `cli(`.** arduino-esp32 defines `cli()` as a macro. Use `os.cli.execute("...")`;
  a standalone `xewe::Cli` object is named `xewe_cli`.
* **Find the source of truth.** `build/` and `src/modules/` (with `Modules.h` and `modules.lock`)
  are regenerated by `./setup.sh`; `XeWeBuildInfo.h` by every build; `library.json` by
  `publish.py manifest`; `MODULES.md` by `tools/validate.py --write-index`. Editing a copy is lost.
  Fix it where it comes from, then regenerate.

## No board is normal

Machines running agents usually have no board. `xewe flash`, `xewe run` and `xewe test` compile
first, then print `compiled, not run: no board attached (<chip>, <bin>)` and exit 0. Hardware tests
are reported as "compiled, not run"; `test_compiles` still really builds. Grep for that line; it
is not an error. Exit 4 (or 1 for `xewe test`) only appears with `--require-board`.

Run the tools as `build/.venv/bin/python -m xewe ...` from a project root (the bare `xewe` script
breaks after the project is moved). One board is attached at a time, and each chip costs about a
minute to compile: build the selected chip while iterating, and `--all-chips` (c3, c6, s3) before
calling a change done.

## Reporting back

* **Say what you actually ran.** "Compiled, not run" is not "passed on a board"; a network call
  or a board you do not have is unverified, and saying so plainly is required.
* **Report failures with their output**, and do not describe work as complete when a step was
  skipped.
* **Flag rule changes.** If you introduce a convention that is not yet written down here or in a
  repository's `AGENTS.md`, say so, so it can be added or rejected.
* **Destructive commands:** `rm -rf` on a path built from a variable needs `${VAR:?}`; prefer
  staging in a temp folder and swapping the result in.
