# AGENTS.md — xewe-labs

Rules for coding agents working in any xewe-labs repository. A repository's own agent files
(`.agents/AGENTS.md` and `.agents/RULES.md`, or a root `AGENTS.md` / `CLAUDE.md`) describe that
repository and win where the two disagree. The organization rules themselves are in
[`guidelines/`](guidelines/); each repository's `RULES.md` summarises the ones that apply to it and
links back. Agents are first-class users of this ecosystem: the commands below are the same ones a
human runs.

## The ecosystem

| `xewe-os` | the firmware template users clone; holds only its own code and `xewe.toml` | [`.agents/AGENTS.md`](https://github.com/xewe-labs/xewe-os/blob/main/.agents/AGENTS.md) |

## Never do these without being asked

* **Git writes.** Agents never run a git command that changes state (commit, tag, push, init,
  history rewrites, branch changes) and never create, rename or archive repositories, pull requests
  or GitHub releases. `xewe release` only *prints* the git/gh commands; leave them for a human.
  Tags and registry entries are public and effectively permanent: a published library version can
  never be reused.
* **Touch `~/.arduino15` or `~/Arduino`,** or run `arduino-cli` directly. The tools use their own
  toolchain in `~/.xewe-os/build-tools/` (shared by all projects; `XEWE_HOME` moves it) and the
  project's `build/`; reuse an installed esp32 core with `./setup.sh --arduino-data DIR`. Never
  delete the shared toolchain as a fix.
* **Flash a board or require one.** No `--require-board`, `--erase`, `./run.sh` or `xewe flash` to a
  real port unless the user asks (`xewe run` erases the flash by default). Compiling is always fine.
* **Edit `xewe.toml`.** Only `xewe manifest update`, `xewe modules select`, `xewe setup --modules`,
  the first-setup menu and `xewe release` write it, and only when asked.
* **Open credentials.** Never open, print or copy a dotenv or key file; the tools read them.

## Code rules that break silently

* **The one include is `#include <XeWeCore.h>`.** arduino-cli discovers a library only from its
  top-level headers; a sketch or module whose only XeWeCore include is `<XeWeCore/<Part>.h>` does
  not build. Sub-headers may follow the umbrella.
* **Module constructors name the Os parameter `host`.** The member is `os`; a parameter named `os`
  hides it. Use `os.serial`, `os.nvs`, `os.cli` in bodies, never `this->os`.
* **Handlers capture `[this]` only.** `[&]` silently binds a shadowing parameter.
* **Never write `cli(`.** arduino-esp32 defines `cli()` as a macro. Use `os.cli.execute("...")`;
  a standalone `xewe::Cli` object is named `xewe_cli`.
* **Find the source of truth.** In a project, `build/` (with `build/modules/` and `modules.lock`)
  and `src/Modules.h` are regenerated by `./setup.sh`; `XeWeBuildInfo.h` by every build;
  `library.json` by `publish.py manifest`; `MODULES.md` by `tools/validate.py --write-index`.
  Editing a copy is lost. Fix it where it comes from, then regenerate.
* **Comments describe the code**, never the process that produced it: no agent or session names,
  dates, decision ids or "was …" history ([`guidelines/documentation.md`](guidelines/documentation.md#no-process-in-code-or-docs)).

## No board is normal

Machines running agents usually have no board. `xewe flash`, `xewe run` and `xewe test` compile
first, then print `compiled, not run: no board attached (<chip>, <bin>)` and exit 0. Hardware tests
are reported as "compiled, not run"; `test_compiles` still really builds. Grep for that line; it
is not an error. Exit 4 (or 1 for `xewe test`) only appears with `--require-board`. In a
compile-only session set `XEWE_NO_BOARD=1`: no port is listed, probed or opened.

Run the tools as `build/tools/.venv/bin/python -m xewe ...` from a project root (the bare `xewe`
script breaks after the project is moved). One board is attached at a time, and each chip costs
about a minute to compile: build the selected chip while iterating, and `--all-chips` (c3, c6, s3)
before calling a change done. Core and module changes are tested in a copy of the template (a
harness) set up from local checkouts: `XEWE_TOOLS_SOURCE`, `XEWE_CORE_SOURCE`,
`XEWE_MODULES_SOURCE`.

## Reporting back

* **Say what you actually ran.** "Compiled, not run" is not "passed on a board"; a network call
  or a board you do not have is unverified, and saying so plainly is required.
* **Report failures with their output**, and do not describe work as complete when a step was
  skipped.
* **Flag rule changes.** If you introduce a convention that is not yet written down in
  `guidelines/` or in a repository's agent files, say so, so it can be added or rejected.
* **Destructive commands:** `rm -rf` on a path built from a variable needs `${VAR:?}`; prefer
  staging in a temp folder and swapping the result in.
